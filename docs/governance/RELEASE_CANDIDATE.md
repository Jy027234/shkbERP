# 安全发布候选流程

发布候选是可追溯的源码、后端 jar、前端产物、迁移目录和本地镜像的固定组合；它不是生产发布许可。

当前产品的生产部署锁保持开启。候选标签只能证明：

- 源码来自规范单体仓库的 main；
- Java 25、前端 Node 24 和完整门禁已通过；
- 迁移目录已逐文件哈希校验；
- 本地隔离恢复演练已通过；
- 产物哈希已写入不可变 Git 注释标签。

它不证明云端的实际 schema、菜单、历史数据或外部依赖已通过验收。

## 创建候选

先确保 main 干净、已合并待发布改动，并选择未使用的日期式版本号：

~~~
powershell -ExecutionPolicy Bypass -File .\scripts\new-release-candidate.ps1 -Version v2026.08.15-rc.1
~~~

该命令会依次执行：

1. scripts/verify-all.ps1 -Full -Install -Candidate；
2. 本地 verify-release-restore.ps1；
3. 构建 xingyun-api.jar、前端 dist 和本地 Docker 镜像；
4. 在系统临时目录生成 JSON 候选清单；
5. 创建指向验证提交的 Git 注释标签。

标签注释中固定记录源提交、jar SHA-256、前端文件树 SHA-256、迁移目录/计划 SHA-256、镜像 ID、恢复演练证据 SHA-256 和候选清单 SHA-256。候选清单在本地临时目录中可作为后续 GitHub Release 附件保存；它不应包含数据库导出或凭据。

默认只创建本地标签。经代码评审后再明确推送：

~~~
git push origin v2026.08.15-rc.1
~~~

也可以在已确认需要推送标签时使用 -Push。候选流程不会启动、替换或重启任何运行中的 Docker 容器。

## 状态边界

| 状态 | 可做的事 | 不可做的事 |
| --- | --- | --- |
| 开发门禁通过 | 继续开发、提交、创建 PR | 宣称可生产发布 |
| 本地候选标签完成 | 保存可复现证据、进行恢复副本验收准备 | 修改云端、执行生产 SQL、解除发布锁 |
| 生产恢复副本验收完成 | 准备变更窗口、评审回退方案 | 未经明确授权直接部署 |
| 明确生产批准 | 在批准窗口按单独运行书执行 | 将历史初始化 SQL 当作增量迁移 |

真正的生产发布仍需按 [MIGRATION_SAFETY.md](MIGRATION_SAFETY.md) 的恢复副本、业务确认、备份和授权条件执行。
