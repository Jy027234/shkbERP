# 上海凯奔 ERP 唯一源码与发布治理

## 决策

`git@github.com:Jy027234/shkbERP.git` 是上海凯奔 ERP 唯一发布入口。它同时保存 `erp-backend` 和 `erp-frontend`，一个 Git 提交必须能够唯一确定前端、后端、数据库迁移和验证脚本。

工作区旁的旧 `erp-backend`、`erp-frontend` 独立仓库仍含未合并内容，因此暂时作为“迁移输入”只读保留。它们不是发布源，也不得用于构建生产 jar、前端静态包或 Docker 镜像。

## 当前为什么禁止发布

2026-08-14 的逐文件 SHA-256 对账发现：

- 后端有 2319 个相同文件、33 个同路径但内容不同的文件。
- 旧独立后端独有 5 个文件，其中包括上海凯奔菜单/角色基线迁移与验证脚本。
- GitHub 单体仓库后端独有 28 个文件，其中包括健康检查、备份恢复、RabbitMQ 失败恢复、核心物料规则和事务 Outbox。
- 前端有 2122 个相同文件，仅 `package.json` 存在 1 处工作区布局差异。

任意一边直接覆盖另一边都会丢失已完成工作。因此 `source-baseline.json` 当前明确设置 `release.deploymentAllowed=false`，正式发布检查必须失败，直到差异逐项合并并验证。

第二阶段已对 33 个同路径后端差异逐项分类，并将菜单/权限迁移、菜单探针和 10 个上海凯奔默认租户脚本合入单体仓库；22 个健康、备份、消息可靠性和事务相关文件保留单体仓库版本。详细决策见 `BACKEND_RECONCILIATION.md`。组合迁移、直连/单体代理菜单探针和前后端静态门禁均已通过；最新候选 `v2026.08.16-rc.3` 已创建并记录制品与恢复证据哈希。已授权的生产逻辑备份副本已在本地隔离 MySQL 完成技术预检、两轮候选迁移演练及候选镜像的八组核心只读 API 验收；当前仍需完成 V1.21 业务确认、合同/采购/库存等人工业务验收、回退方案和明确发布批准，部署锁不解除。

## 云端定位

云端现网只作为冻结业务参照：当前观察到的后端是 Java 8 / Spring Boot 2.2.2 jar，前端静态包与后端构建物均未携带可核验 Git 提交号。2026-08-16 已对云端运行物与最新逻辑备份做只读核对，并将经过 SHA-256 校验的备份副本恢复到本地受限数据库；该过程没有上传文件、执行生产 SQL、重启服务或修改配置。

未来发布必须先在云端恢复副本或隔离演练环境完成数据备份、增量迁移、登录、菜单和核心业务验收；只有用户明确批准某个带标签的发布版本后，才能另行制定生产切换步骤。

2026-08-16 的本地恢复副本 API 启动诊断发现，历史 `tenant` 数据中的动态 JDBC 配置由生产 Jugg 密钥加密；本机候选的本地密钥不能解密该历史记录。此发现没有保存密钥、密钥指纹、加密记录或云端地址。后续恢复副本 API 验收必须由获授权人员通过受控会话注入保持连续的 `JUGG_SECRET_KEY`，并以候选成功达到 readiness 作为证明。禁止通过生成新密钥、把密钥写入仓库或改写生产租户 JDBC 密码来绕过该门禁。

V1.36 起，迁移分类、SQL 哈希、存量库候选计划、本地预检和本地恢复演练由 migration-catalog.json 与 MIGRATION_SAFETY.md 固化。候选标签会记录前后端产物、迁移计划和恢复演练的哈希，但不改变云端只读策略，也不解除生产锁。

## 固定规则

1. 新开发只在本仓库的任务分支进行。
2. 一个发布版本只对应一个 Git 标签、一个提交和一组不可变镜像摘要。
3. 禁止从脏工作树部署；禁止将独立仓库的 Vite 与本仓库后端镜像混用。
4. 数据库只允许增量迁移，严禁对已有数据库执行 `V1.0__init.sql`。
5. 每个业务模块必须在 `SHKB_MODULE_MATRIX.md` 记录代码、schema 和验证证据。
6. `scripts/verify-source-baseline.ps1 -Release` 是发布前置门禁，不得绕过。
7. 旧仓库只有在差异完成对账、形成可追溯提交并保留归档标签后，才可停止作为迁移输入。
8. 任何存量库迁移必须先通过迁移目录校验和隔离恢复副本预检；历史初始化和历史重建 SQL 不得混入候选计划。
9. 候选版本由 new-release-candidate.ps1 创建；候选标签不是生产授权，生产恢复副本和明确批准仍是独立阻断项。

## 对账顺序

1. 已合并旧独立后端的菜单/权限基线，并保留 GitHub 侧 Outbox、健康和消息可靠性改进。
2. 已逐个审查 33 个内容不同文件，禁止目录级覆盖。
3. 已确认前端 `package.json` 应保留单体仓库工作目录语义。
4. 已运行源码门禁、前后端静态门禁、数据库迁移幂等验证和菜单业务冒烟。
5. 已建立独立干净治理提交、创建带标签候选，并完成授权生产备份副本的技术恢复及核心只读 API 验收；该 API 验收已通过历史 Jugg 密钥连续性门禁。只有 V1.21 业务确认、核心业务验收、回退方案和明确批准等发布阻断项关闭后才可评估将 `deploymentAllowed` 改为 `true`。
