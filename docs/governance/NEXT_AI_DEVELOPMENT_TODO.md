## 3. 源码启停总表

状态含义：

- **本地可用**：有 schema、接口和关键本地写流程证据，可继续做局部修复或验收。
- **条件可用**：代码可编译或已有只读证据，但仍缺业务配置、完整写流程、外部协议或恢复副本验收。
- **局部禁用**：模块主体可用，但明确的一类动作必须继续阻断。
- **禁用/非发布范围**：不得投入开发、补迁移、加入菜单、加入核心回归或发布。

| 现网业务/源码区域 | 当前结论 | 可做的工作 | 尚未覆盖或必须保留的限制 |

## 4. 明确禁用和不得误用的源码

### 4.1 产品范围禁用

| 源码 | 位置示例 | 规则 |
| --- | --- | --- |
| 销售订单、销售出库、销售退货、销售参数 | `erp-frontend/src/views/sc/sale`、`erp-frontend/src/api/sc/sale` 及对应通用后端代码 | 上海凯奔原设计和现网均没有销售功能。不得补 schema、补菜单、补 E2E、扩展功能或发布。不要贸然物理删除可能被通用库存依赖的类。 |
| 成品出入库 | `erp-frontend/src/views/product-storage`、`erp-frontend/src/api/shkb/product-storage`、`ProductStorageController` 及附件服务 | 半成品且不在现网范围。不得补迁移、加入菜单、加入核心回归或发布。 |

只有用户明确改变产品范围，并给出业务流程、角色权限、数据模型和验收标准后，以上模块才能另立专题重新评估；“代码已经存在”不是启用理由。

### 4.2 技术和运维禁用

1. 禁止从工作区旁的旧拆分仓库构建或发布。
2. 禁止把 `erp-backend/cloud` 两个未纳入主 reactor 的模块当成已验证功能。
3. 禁止对已有数据库执行平台或租户的 `V1.0__init.sql`；它们只允许初始化确认无数据的空库。
4. 禁止补跑 `migration-catalog.json` 中标记为 `historical-baseline-only` 的历史脚本。
5. 禁止修改已登记迁移的内容。`V1.26__shkb_hr_core.sql` 已固定哈希；后续结构变化必须新增 `V1.27` 或更高版本并登记目录。
6. `V1.21__shkb_menu_permission_baseline.sql` 包含受控数据修改，未完成业务确认前不得对生产执行。
7. 禁止为批次/序列号盘点、调整、调拨绕开现有安全阻断；先取得明细级业务契约，再实现库存、批次和序列号同步事务。
8. 禁止新增跨租户运营、租户切换矩阵或多租户产品能力。现有租户字段仅为框架和存量数据兼容。
9. 禁止把真实生产凭据、Jugg 密钥、数据库备份、部署包、云端地址或审计临时文件提交进仓库。
10. 禁止创建新发布候选、标签或执行生产变更，除非用户针对该动作另行明确授权。

## 5. P0：下一位 AI 应执行的人事管理专题

### 5.1 目标

在仅使用本地隔离数据库、测试账号和测试文件的前提下，证明以下七项现网功能能同时通过后端直连和前端 Vite `/api` 代理完成认证后的关键读写流程：

1. 员工档案
2. 证书管理
3. 培训记录
4. 培训课程
5. 培训实施
6. 授权项目
7. 人员授权

目标是把 HR 从 L2 提升到有证据的 L3/L4；不是部署生产，也不是复制生产人员数据。

### 5.2 先处理菜单和权限缺口

当前版本化迁移中没有 HR 菜单、角色和权限数据；`V1.26` 只建立 HR 业务表，`V1.21` 也未包含七项 HR 菜单。不得猜测生产菜单 ID、角色关系或权限码。

允许的做法：

- 从已获授权的业务配置说明中核对路由、组件、权限码和角色范围；或
- 在专题验证脚本中创建**硬限制为本地隔离库**、带唯一前缀并能精确清理的菜单/角色夹具。

如果缺少业务确认，允许先完成 API 直连验证和本地临时权限夹具验证，但必须把正式菜单迁移列为未完成，不能擅自生成生产增量 SQL。

### 5.3 建议新增专题脚本

新增 `erp-backend/scripts/verify-hr-flow.ps1`，沿用已有 `verify-contract-flow.ps1`、`verify-equipment-flow.ps1` 的安全模式：

- 只接受 `127.0.0.1`、`localhost` 或仓库明确的本地 Docker 容器；发现公网地址或非测试数据库立即失败。
- 使用唯一运行前缀创建员工、证书、课程、培训实施、参与人、授权项目和人员授权夹具。
- 同一套断言分别对后端直连地址和 Vite `/api` 代理执行。
- 所有写入、上传文件、角色/菜单夹具和日志都在 `finally` 中精确清理；成功后断言残留为 0。
- 不读取生产账号文件，不连接生产数据库，不使用生产备份作为日常开发库。
- 测试失败时保留足够诊断信息，但不得输出 token、密码、文件系统真实根路径或人员数据。

### 5.4 最小读写验收矩阵

| 功能 | API 前缀 | 最少必须验证 |
| --- | --- | --- |
| 员工档案与文件 | `/shkb/employee`、`/shkb/employee-file` | 查询、详情、新增、修改、离职状态、统计；上传/列表/下载/删除；删除或无效引用守卫 |
| 证书 | `/shkb/employee-certificate` | 新增、修改、按员工查询、统计、导出、删除；员工归属和无效员工守卫 |
| 培训记录 | `/shkb/employee-training` | 新增、修改、按员工查询、统计、导出、删除；员工归属守卫 |
| 培训课程与文档 | `/training-course` | 新增、修改、启停、详情、有效列表、导出；课程文档上传/列表/删除 |
| 培训实施与参与人 | `/training-implementation`、`/training-participant` | 创建、参与人批量维护、开始、完成、取消；完成时参与人结果与员工培训记录在同一事务边界正确落库，失败时整体回滚 |
| 授权项目 | `/shkb/authorization-project` | 新增、修改、启停、有效列表、必修课程关系、导出和删除引用守卫 |
| 人员授权与附件 | `/shkb/person-authorization` | 新增、修改、项目关系、延期、撤销、有效性检查；附件上传/列表/下载/删除 |

通用断言还必须覆盖：

- 未登录返回 401，缺权限返回 403；错误体继续使用 `code`、`msg`、`traceId`。
- 直接后端和 Vite 代理的 URL、方法、参数位置、响应包装和下载响应一致。
- 附件下载拒绝 `..` 路径逃逸、上传根目录外的本地路径和外部 `://` URL；错误信息不得泄露真实文件路径。
- 文件名使用安全的 `Content-Disposition` 编码，未知 MIME 回退到 `application/octet-stream`。
- 重复开始、完成、延期、撤销和删除的状态规则有明确结果；需要并发控制的动作至少验证一次重复提交。
- 导出遵循项目现有 10000 条上限，不通过扩大上限回避分页或内存问题。

### 5.5 P0 完成定义

只有同时满足以下条件，才能把 HR 的矩阵等级从 L2 提升：

1. `V1.26` 在一次性 MySQL 8 首次和重复执行均成功，13 张表齐全；不修改该迁移文件。
2. 新增的 HR 专题脚本在后端直连与 Vite `/api` 两条链路都通过，测试夹具和测试文件残留为 0。
3. 至少覆盖员工、证书、培训实施完成事务、人员授权和附件安全边界的失败路径。
4. 后端 Java 25 全 reactor 验证、前端类型检查、27 项既有 Vitest 加新增测试、生产构建全部通过。
5. 更新 `SHKB_MODULE_MATRIX.md`、`CODEX_HANDOFF.md`、两端 `UPGRADE.md` 中受影响的状态、命令、日期和未覆盖风险。
6. 明确记录 HR 菜单/角色采用的是“已确认正式配置”还是“仅本地夹具”；后者不能作为生产迁移证据。

## 7. P2：中期技术债与可靠性优化

- 维修看板：与业务负责人核对指标口径、空值、时间范围和权限过滤，增加前端交互 E2E。
- 自动化设备：完成真实线束检测机、磁粉机协议联调，覆盖下发成功后断电、重复上报和乱序状态。
- 消息和后台任务：补齐其余 RabbitMQ 生产点、定时任务、WebSocket 的事务、重试、幂等和停机恢复测试。
- 公共错误与安全：持续验证 400/401/403/409/500 的统一响应，补文件权限、越权访问和大文件边界测试。
- 前端性能：在不改变业务行为的独立专题中处理超大 chunk 和 Browserslist 数据；依赖族一次只升级一个。
- 后端兼容债：分专题移除 Swagger 2 编译兼容层，验证 Jugg inner 双栈；不要与 Spring Boot 大版本升级同时进行。
- `cloud` 模块：先独立编译、运行和确定产品是否需要，再决定是否纳入主 reactor；在此之前保持未验证状态。

销售和成品出入库不属于 P1/P2 优化清单；它们是冻结范围，不应以“清理技术债”为理由重新投入。

## 8. 每轮开发的验证门禁

根目录：

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\verify-source-baseline.ps1
powershell -ExecutionPolicy Bypass -File .\scripts\verify-migration-catalog.ps1 -Plan All
git diff --check
```

后端发生变化：

```powershell
Set-Location .\erp-backend
powershell -ExecutionPolicy Bypass -File .\scripts\verify.ps1
```

前端、API 契约、认证、代理或下载行为发生变化：

```powershell
Set-Location .\erp-frontend
powershell -ExecutionPolicy Bypass -File .\scripts\verify.ps1
```

涉及现有业务模块时还要运行对应 `erp-backend/scripts/verify-*-flow.ps1`。所有写流程脚本只能指向本地隔离库；不得为了让脚本通过而弱化公网地址阻断、夹具清理、库存追溯或权限断言。

当前工作树不干净且生产锁关闭，不应运行 `new-release-candidate.ps1`。即使未来创建了新候选，候选也不等于生产授权。

## 9. 必须暂停并请求用户确认的情况

遇到以下情况不得自行假设：

- 需要确定 HR 正式菜单 ID、组件路由、权限码或角色范围；
- 需要确定批次/序列号盘点、调整或调拨的明细业务规则；
- 需要修改或执行 V1.21 的受控菜单/角色数据；
- 需要接入真实设备、真实文件存储、生产备份或历史 Jugg 密钥；
- 需要发布、上传、执行生产 SQL、重启或解锁 `deploymentAllowed`；
- 发现现网范围与 `PRODUCTION_FUNCTION_BASELINE.md` 冲突；
- 发现当前未提交 HR 改动与用户新改动重叠且无法安全合并。

## 10. 下一位 AI 的交付格式

完成一个专题后，交付说明至少包含：

1. 完成了哪个现网业务目标，哪些范围明确没有改；
2. 修改文件和新增迁移/脚本；
3. 实际执行的验证命令、结果和日期；
4. 失败路径、事务、并发、权限、附件和清理证据；
5. 模块等级是否变化，以及为什么；
6. 仍未覆盖的业务确认和生产阻断项；
7. 明确声明是否对云端有任何写入。默认答案必须是“没有”。
